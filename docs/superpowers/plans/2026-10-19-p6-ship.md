# Future Flow P6: ship (judge eval, deploy, release APK, README demo) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Future Flow runs for real on the owner's Redmi (spec §16 P6: "Maestro E2E, judge eval, README + demo GIF, EAS release `v1.0.0`"):

1. **Judge eval** (spec §14).
   - About 50 labelled GitHub and reading cases, run through the production judge path (`judgeGithub`, `judgeReading`, the same router and models).
   - It measures accuracy, false passes and the auto-decide coverage at the 0.75 threshold, and writes a report.
   - `JUDGE_AUTO_DECIDE` stays off until an ADR records a passing measurement.
2. **Deploy the Worker.**
   - npm scripts for the remote migrations and the deploy.
   - A runbook the owner follows once: `wrangler login`, `d1 create`, secrets, deploy.
   - A startup check that refuses to run without `SETUP_CODE`.
3. **Release APK.**
   - An EAS `production` profile: an APK with the deployed Worker URL, no E2E flags.
   - A `Release` workflow on `v*` tags (spec §14: EAS builds only on tags, 15 a month) that needs the `EXPO_TOKEN` secret.
   - The app version becomes 1.0.0.
4. **README and demo GIF.**
   - The emulator run turns its screenshots into `demo.gif` (ffmpeg on the runner), and the GIF is committed under `docs/`.
   - The README covers what it does, the privacy model, how to run it, how to deploy and how to release.

**Owner steps (they can't be done by Claude: they need the owner's accounts and keys):**

- **Cloudflare:** `! bun x wrangler login`, then follow `docs/deploy.md` (create D1, paste the id, set the secrets, deploy).
- **Keys:** GEMINI_API_KEY and JEV_API_KEY in `apps/api/.dev.vars` to run the eval locally (`bun run judge:eval` in `apps/api`), and as Worker secrets for production.
- **Expo:**
  - `! bun x eas-cli login`, then `bun x eas-cli init` once (prints the project id)
  - add `EXPO_TOKEN` and `EAS_PROJECT_ID` to the GitHub repo secrets
  - push the tag `v1.0.0`

**Spec:** §14 (judge eval, EAS on tags), §15 (secrets only in Worker secrets), §16 P6, ADRs 0008, 0012.

## Global Constraints

- Machine limits as before: one test file at a time, no repo-wide commands. Never `expo prebuild` or `export` locally.
- Bun only. No AI attribution. Secrets never in the repo; `.dev.vars` stays gitignored.
- The eval runner never prints keys or full prompts; the report holds case ids, labels, decisions and metrics.
- The emulator run is on demand, once, at the end.

## Review Focus

1. The eval scores exactly what production would decide (same state builders, same threshold), and an unavailable provider is reported as such, not as a wrong answer.
2. **The labels:** each case's expected outcome is clear from its criteria alone.
3. **Release safety:** a store APK can't get E2E flags, an http API URL, or a missing API URL.
4. **The deploy runbook:** it's complete, in order, and never asks the owner to commit a secret.

### Task 1: Judge eval

- [ ] **Pure `apps/api/src/verification/eval.ts`, tested in Vitest:**
  - `scoreCase(expected, decision, threshold)`
    - **outcome:** correct, false pass, false fail, or unavailable
    - **auto:** whether the decision would be decided on its own
  - `summarize(results)`
    - **counts:** accuracy, auto coverage, auto accuracy, false passes overall and when auto
  - `gate(summary)`, which allows auto-decide when there are at least 40 judged cases, the auto-decided accuracy is at least 95%, and there are no auto false passes
  - `report(summary, results)`, a Markdown table
- [ ] **`apps/api/eval/judge-cases.ts`:** 50 cases (25 GitHub, 25 reading), mixing clear passes, clear fails and near misses, each with a one-line note on why.
